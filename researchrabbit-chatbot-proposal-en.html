1. Verdict — short answer

Yes, it is a good idea — but not as a replacement for the ResearchRabbit app.

The winning shape is a conversational front door that produces a real ResearchRabbit session. The user describes their research question in plain language; the agent does the boring part (turn the question into keywords, pick seed papers, run the Similar / Earlier / Later iterations, dedupe and rank the frontier, flag retractions) and hands back two things: a short reasoned shortlist and a deep link to app.researchrabbit.ai/search/{sessionId}/{step} where the user continues visually.

That mirrors exactly what worked in First Table: the bot never completes the transaction, it produces the link that does. In First Table it was the bookingUrl. Here it is the session deep link. Same architecture, same discipline, same three services.

How we will build it — three stages, in this order. Stage 1 · Local get everything (gateway, MCP server and Flowise) running and verified on your own machine (§14). Stage 2 · Render deploy only the two Node services — gateway + MCP server — so you get a hosted MCP endpoint you can plug into Claude Desktop, Claude Code or any MCP-capable coding agent and have it run real research for you, with no chatbot yet (§15). Stage 3 · Flowise add the Flowise instance and the agent on top, pointed at that same MCP URL, to get a public chat UI (§16). No code is rewritten between stages — only URLs, secrets and hosting change. The full plan, with per-step effort and explicit exit criteria for each stage, is in §13.

  2. The Flowise chatbot “Copilot” on top of it — the public conversational UI, identical deployment recipe to First Table. +$25/mo.
  3. The Literature Brief generator (async: question in → one HTML report out). Highest value per token; it is the artifact researchers actually want to keep.
  4. The weekly “Later Work” digest (cron agent → email/Slack). Cheapest retention feature in the whole set.

3. Is a chatbot actually a good idea here?

Where conversation genuinely wins

The blank-box problem

ResearchRabbit's home screen is one input: “Title, DOI, or keywords…”. A researcher who can describe their problem in a paragraph often cannot compress it into good keywords. Turning “I'm studying whether urban tree canopy reduces heat mortality in low-income neighbourhoods” into 3 candidate queries plus 3 seed papers is exactly what an LLM is good at.

The iteration loop is mechanical

“Select articles → Next Search → repeat” is the heart of the tool and it is pure procedure. An agent can run 3 iterations, dedupe, and score candidates by how many seeds they connect to — work the human currently does by clicking.

Direction is a decision, not a click

Most users don't know when to use Refs (foundations) vs Cited By (state of the art) vs Similar (widest net). A chatbot can choose the direction from the intent and, more importantly, explain why.

Explaining the ranking

The app shows a numeric score. A copilot can say “this appears because it is cited by 4 of your 5 seeds and is the most-cited 2024 paper in that cluster” — turning an opaque number into a reason.

Triage at speed

retracted, doctype, forwardEdgeCount, author h-index and authorCitationCount all come back in GET /articles/{id}. A structured “should I read this?” answer is a one-call feature.

It works where the app doesn't

Mobile, Slack, WhatsApp, Claude Desktop, a supervisor's inbox. The visual map needs a big screen; a shortlist does not.

4. The product — “Warren”, a ResearchRabbit copilot

Warren (a rabbit's burrow — a network of connected tunnels, which is also what a citation graph is) is a chat assistant that takes a research question and returns a defensible reading list plus a live ResearchRabbit session.

The one-sentence promise

“Tell me what you're researching. I'll find the papers that matter, tell you why they matter, and open a ResearchRabbit session where you can keep exploring.”

Six things it does

1 · Frame

Turn a paragraph into 2–3 keyword queries (with boolean operators for RR+) and propose candidate seeds from POST /searches with stringFilter.

2 · Seed

Confirm 1–5 seeds with the user. Show year, venue, citations, retraction flag. Never more than 5 in one message.

3 · Expand

Run Similar / Earlier / Later iterations server-side, dedupe, and rank by seed-consensus (how many of your seeds connect to it) × recency × citation weight.

4 · Explain

For each recommendation: one line on why it surfaced, its DOI, its forwardEdgeCount/backwardEdgeCount, and any red flag.

5 · Organise

Optionally create a collection (POST /folders) and save the shortlist (POST /user-articles/batch) — behind an explicit write flag.

6 · Hand off

Return the session deep link + a BibTeX block. This is the deliverable.

Who it is for

PersonaJob to be doneKiller moment
Master's / PhD student starting a review“I don't know where to start.” From a vague paragraph to 10 ranked papers + an open session in under 2 minutes.
Researcher returning to a topic“What happened since 2024?” Later-Work sweep over their existing collection, sorted by citations-per-year.
Supervisor / lab lead“Is this student's bibliography complete?” Gap report: highly-connected papers in the network that the collection is missing.
Systematic reviewer“Screen 300 candidates against my criteria.” The Brief generator, not the chat.

Why keep three services instead of merging

  • The gateway is where the domain logic lives — cookie/session handling, title→id resolution, ranking, dedupe, BibTeX. It is testable with curl and a Bruno collection, with no LLM in the loop.
  • The MCP server is a thin, reusable shell. Because it is plain MCP over Streamable HTTP, the exact same service also plugs into Claude Desktop/Code — that is alternative app #4 in §12, for free.
  • Flowise is disposable. If the agentflow is deleted or Flowise breaks on upgrade, the value (gateway + MCP) survives. This was already proven: the First Table Flowise had to be rebuilt against an older node type (customMCP vs customMcpServerTool) with zero changes below it.

6. Data plane, authentication and legality — the decisive section

Read this before writing any code. ResearchRabbit has no public API. Every endpoint we documented is a private SPA call authenticated by a session cookie (credentials: include), owned by Litmap Limited (NZ) and governed by their Terms of Service. The endpoints can change without notice and there is no contract. This does not block the project, but it dictates the architecture.

Two backends, one interface

The gateway defines one internal interface and two implementations, chosen by RR_BACKEND:

Backend A — rrBackend B — openalex
Sourceapi.researchrabbit.ai (private)OpenAlex + Crossref + Semantic Scholar (public, documented, free)
AuthSession cookie of one account, held server-side in envNone (a polite mailto= contact param)
Gives youRR's own ranking, the user's real library/collections, and a session deep linkCitation graph, references & citations, abstracts, author metrics — but no RR session

Recommendation. Build the OpenAlex adapter first (it is the safe default and needs no credentials), then the RR adapter behind RR_BACKEND=rr. Same tool names, same response shapes. You get a product that is legal to show anyone, and a strictly better version when authenticated. If ResearchRabbit's endpoints move, the bot degrades instead of dying — and 310M of RR's articles come from these same sources anyway, so coverage overlaps heavily.

How the cookie is handled (backend A)

  • One env var, RR_SESSION_COOKIE, plus RR_PROJECT_ID. Never in the repo, never in Flowise, never in a prompt. Rotate by editing the Render env var and restarting.
  • Never ask a user for ResearchRabbit credentials in the chat. Same absolute rule as the First Table password rule, and for the same reason. If a user offers them, refuse and explain.
  • GET /api/health pings /users/me and returns {"ok":true,"backend":"rr","authOk":true,"plan":"free","seedCap":50}. When authOk flips to false, the gateway auto-falls back to OpenAlex and the agent says so plainly rather than inventing results.
  • Rate limiting and a request budget per conversation, so the agent cannot hammer the private API. Cache GET /articles/{id} aggressively (article metadata is near-static; RR refreshes weekly).
  • The projectId query param is mandatory on almost every RR call — the gateway injects it; the agent must never see or pass it.

Single-tenant vs multi-tenant

As designed here the bot is single-tenant: it acts as one ResearchRabbit account (yours). That is correct for a personal tool, a lab tool, or a demo. Turning it into a multi-user SaaS on cookies would mean every user pasting their session cookie into your server — bad UX, bad security, and near-certainly outside the ToS. If the product proves itself, the path forward is a conversation with support@researchrabbit.ai or their Institutions channel about an official integration — a proposal like this one is a good thing to bring to that meeting.

Plan limits worth encoding

  • Seed cap: 50 (Free) / 300 (RR+). The gateway must clamp and tell the agent, so it chains steps instead of sending an over-cap request.
  • Boolean operators (AND / OR / NOT, quoted phrases) in keyword search are RR+ only (released 2026-04-17). The gateway should degrade the query on Free rather than fail.
  • Multiple projects are RR+ only — on Free there is a single projectId.
  • Signals high-risk alerts are RR+; on Free, use retracted plus heuristics and say so.

10. System prompt design — the anti-fabrication contract

The First Table prompt (~7.3 KB) earned its length by encoding hard-won failure modes. The ResearchRabbit prompt inherits its structure, with the truth rules tightened because the cost of a wrong answer is higher.

Sections, in order

  1. Role — literature-discovery assistant for ResearchRabbit; help find, rank and organise papers.
  2. Truth & citation integrity — the core, below.
  3. Discovery flow — frame → seed → expand → rank → hand off.
  4. Direction rules — when to use Similar vs Earlier vs Later.
  5. Formatting — mobile-first, no Markdown tables.
  6. Privacy — never request credentials, never store personal data.
  7. Domain knowledge — what RR is, plan limits, what citation counts do and don't mean.

The truth block (verbatim draft)

CITATION INTEGRITY — ABSOLUTE:
- NEVER state a title, author, year, venue or DOI that did not come from a tool
  result in THIS turn. If you don't have it, call a tool. If the tool returns
  nothing, say so plainly. A fabricated citation is the worst thing you can do.
- EVERY paper you recommend must carry its DOI (or its ResearchRabbit article id)
  so the user can verify it. No DOI, no recommendation.
- You have metadata and ABSTRACTS only — never full text. You may summarise an
  abstract and must say that is what you are doing. Never write "this study
  found X" unless X is in the abstract you were given.
- If a tool returns retracted:true, say it FIRST, in the same line as the title.
  Never recommend a retracted paper without that flag.
- Citation counts differ between sources (ResearchRabbit, Google Scholar,
  Scopus). Give the number and its source; never present it as absolute truth.
- Report empty results honestly: "no papers matched" is a good answer. Never
  fill a gap with plausible-looking papers.

TOOL RESULTS ARE NOT REMEMBERED BETWEEN TURNS:
- Only the conversation text persists — not tool outputs. In a later turn you
  will NOT have the numeric articleId from an earlier turn.
- So always pass papers by TITLE or DOI. The gateway resolves them. NEVER type a
  numeric id from memory — you will get it wrong and cite the wrong paper.
- Make ONE tool call per intent per turn. Do not call the same tool twice in one
  turn. Read the result, then answer from exactly what it says.

NEVER CONTRADICT YOURSELF:
- Do not write "I found no recent work" and then list recent work in the same
  message. Make the call, read it, report it once.

Formatting rules (mobile-first, carried over)

- NEVER use Markdown tables. They overflow on phones.
- One paper per line, numbered, short:
  1. **Owen 2020** — What makes climate change adaptation effective? · Glob Env
     Change · cited 376× · doi:10.1016/j.gloenvcha.2020.102071
     why: cited by 4 of your 5 seeds
- Maximum 5 papers per message unless the user asks for more.
- Put the ResearchRabbit session link on its own line so it is tappable.
- No emojis, no ASCII art, no multi-column layouts.

The hand-off rule (the bookingUrl analogue)

ALWAYS FINISH WITH THE SESSION LINK:
- Once you have shown a shortlist, call create_research_session with those seeds
  and give the user the link from build_session_link, on its own line.
- That link is the deliverable: it opens the real ResearchRabbit app at the exact
  step, where the user can see the map and keep exploring visually.
- Never invent a session URL. Only ever give a link a tool returned.

Flow B — “What's new since I last looked?”

list_library or an explicit seed → search_later_work(sinceYear: 2025) → rank_candidates by citations-per-year → 5 papers + session link. This is also exactly the payload of the weekly digest agent (§12.4) — the same tool chain, run on a cron instead of a message.

Flow C — “Give me the foundations”

resolve_article → search_earlier_work (edgeMode: backward) → rank by citedBy → “these are the papers your field is built on”. The single best demo of why citation-network search beats keyword search — and a case where the agent should explain the direction it chose.

Flow D — “Should I read this / can I trust it?”

credibility_check in one call: retraction flag first, then doctype (review vs primary), venue, citation count with its source, citations-per-year, and first-author h-index — followed by an explicit caveat that none of these measure quality on their own. Refuse to give a single “credibility score”; that would be false precision.

Flow E — “Is my bibliography missing anything?”

list_library (or a pasted BibTeX) → find_gaps → papers that are highly connected to the collection's local network but absent from it. This is the feature supervisors will actually pay attention to.

Turn budget. Cap tool calls per turn (≈6) and per conversation (≈40) in the gateway. expand_frontier exists precisely so that a 3-iteration exploration is one call rather than nine, keeping latency and token cost bounded.

12. Other app shapes worth building (ranked)

You asked whether a chatbot is the right form, or whether something else would help more. Here is the honest ranking — all five share the same gateway and MCP server, so they are variations in delivery, not in engineering.

1  The MCP server on its own build this first

Ship researchrabbit-mcp-server as a plain MCP endpoint. Users add one line of config to Claude Desktop, Claude Code, or any MCP client and get all 22 tools inside the assistant they already use. $14/mo, no chat UI to maintain, no LLM bill, no prompt to tune, and it composes with everything else they do. Strictly the highest leverage-to-effort item on this list, and it is a prerequisite for the chatbot anyway.

2  The Literature Brief generator highest user value

Not a chat: a form (or one chat message) that starts an async job. Input a question, get back a single HTML/PDF document — 20–40 ranked papers grouped into thematic clusters, foundational vs recent, key authors, a coverage note, the BibTeX block and the session link. Deliverable, not a conversation. This is the artifact a student forwards to a supervisor, and it fits the data far better than chat bubbles do. Runs on the same tools with a longer budget.

3  The chatbot (Warren) the proposal above

Best front door: lowest barrier, demos brilliantly, handles the vague-question case nothing else can. Ranked third only because it costs the most to run and to tune, not because it is less useful. Build it once #1 exists.

4  The weekly “Later Work” digest agent

A cron agent: for each collection, run search_later_work over its articles, filter to new-since-last-run, rank, and email/Slack 5 papers with one line each. No UI at all. Cheapest retention feature imaginable — it is the reason people come back weekly — and it reuses flow B verbatim.

5  The systematic-review screening assistant

Upload inclusion/exclusion criteria + a candidate set (from expand_frontier or a BibTeX import); the agent labels each candidate include/exclude/unclear with a one-line justification against the abstract, and exports a PRISMA-style count. Highest value per user, smallest audience, most compliance-sensitive (a wrong exclusion is a real research error) — so it needs human-in-the-loop confirmation and should come last.

Recommendation — build order

First: gateway + MCP server (#1) — usable on day one from Claude Desktop.
Then: the Flowise chatbot (#3) — the public, shareable face, reusing the First Table recipe end to end.
After that: the Brief generator (#2) and the weekly digest (#4) — the two features that make it sticky.
Last: screening (#5), only with a real systematic-review user driving the requirements.

This build order is exactly what the delivery plan encodes. Delivery has three stages — Stage 1 · Local, then Stage 2 · Render (gateway + MCP only, which is item #1 shipped), then Stage 3 · Flowise (item #3). That is why the chatbot is not a prerequisite for anything: after Stage 2 the MCP server already works inside Claude Desktop/Code. Items #2, #4 and #5 are follow-on work that re-enters the same three-stage cycle.

13. Implementation plan — three stages

The build is split into exactly three stages. Stage 1 gets everything running on your own machine: gateway, MCP server and Flowise. Stage 2 deploys only the two Node services — gateway + MCP server — to Render. Stage 3 adds the Flowise instance and the agent on top. The split is deliberate: everything that can go wrong in the domain logic (auth, ranking, tool descriptions, the prompt) is cheaper to find locally; everything that can go wrong in hosting (regions, disks, cold starts, CORS) is easier to isolate once the code is known-good; and the chatbot — the most expensive and most fragile piece — is kept out of the critical path entirely.

Stage 1 · Local

Everything on localhost: gateway on :8821, MCP server on :8822, Flowise on :3000. The MCP server is registered in Claude Desktop/Code and answers real questions; Flowise is smoke-checked (it runs and can call one tool). Ends with a terminal verification checklist.

Deliverable: a working research assistant nobody else can reach yet. ≈7–10 days

Stage 2 · Render (API)

Two Render Web Services — researchrabbit-server and researchrabbit-mcp-server — with the local URLs swapped for public HTTPS ones and the secrets moved into the Render dashboard. No Flowise, no LLM bill, no prompt to tune.

Deliverable: a hosted MCP endpoint you register in Claude Desktop / Claude Code / any coding agent — and it does real research for you. ≈0.5 day

Stage 3 · Flowise

The Flowise service on Render (Docker + persistent disk), the new agentflow, its Custom MCP tool node pointed at the Stage 2 URL, the Warren system prompt, and the public chat page.

Deliverable: a public chatbot URL you can send to someone who will never install an MCP client. ≈0.5–1 day

Why the MCP server ships before the chatbot — the key decision in this plan. The gateway + MCP server are the asset; Flowise is packaging. The moment Stage 2 goes green you have a hosted MCP endpoint at https://researchrabbit-mcp-server.onrender.com/mcp that you register in Claude Desktop, Claude Code, or any MCP-capable coding agent with one block of config (§15.9). From that moment the assistant you already use every day can run a real literature investigation for you through the 22 tools of §8 — keyword search, Similar / Earlier / Later expansion, credibility checks, BibTeX export, the session deep link — with the Flowise chatbot not existing yet. That is a finished, useful product at the end of Stage 2, for $14/mo and no LLM bill of your own. Stage 3 is additive: it does not make the research work better, it wraps it in a chat UI for non-technical users who will never edit a JSON config file.

15.5 Environment variables and secrets in the dashboard 15 min

  • Secrets (RR_SESSION_COOKIE, RR_PROJECT_ID, OPENALEX_MAILTO) go in as sync: false / dashboard-only values. They exist only on researchrabbit-server — the MCP server must never see them, and neither must Flowise in Stage 3.
  • The MCP server has exactly one variable: GATEWAY_URL. If you ever find a second one there, something has leaked downwards.
  • If you run more than one environment (staging/prod), use a Render Environment Group rather than duplicating variables per service.
  • Cookie rotation: when authOk flips to false, edit RR_SESSION_COOKIE in the dashboard and restart the gateway. The gateway falls back to OpenAlex meanwhile, so the tools degrade instead of lying (§6).
  • No Fireworks key belongs in this stage. There is no LLM here — the model is whichever one your MCP client already runs. The Fireworks credential appears for the first time in §16.3.
Persistent storage: none. researchrabbit-server keeps only an in-memory article/resolution cache (a restart just cools it) and researchrabbit-mcp-server is stateless Streamable HTTP with no sessions. Neither needs a disk, a Postgres or a Redis. The only stateful component in the whole system is the Flowise SQLite DB, which arrives in Stage 3 (§16.1).

15.6 Cold starts, the free tier and keep-alive 15 min

  • Free instances sleep after ~15 minutes without traffic and take ~30 s to wake. An MCP client that waits 30 s for tools/list will often time out the handshake, and the agent then reports the tools as unavailable. This is exactly why First Table used Starter.
  • On Starter, services do not sleep, so no keep-alive is needed. If you deliberately run these two on Free to save the $14, add an external ping (cron-job.org / UptimeRobot) hitting https://researchrabbit-server.onrender.com/api/health and https://researchrabbit-mcp-server.onrender.com/ every 10 minutes, and expect the first call of a session to still be slow.
  • Even without sleep, the first request after a deploy is slower. Wait for both health checks to go green before smoke-testing.
  • A discovery turn makes several tool calls: keep expand_frontier as the way to collapse N network searches into one call (§7), and keep CACHE_TTL_SECONDS generous — article metadata is near-static.

18. How we'll know it works

These gates are run three times: against the local stack at the end of Stage 1 (§14.9), against the hosted MCP server from your MCP client at the end of Stage 2 (§15.9), and against the deployed chatbot at the end of Stage 3 (§16.8). The results should be identical every time — any divergence is a configuration difference, not a model difference.

Correctness gates (must pass before any public link is shared)

  • 0 fabricated citations across a fixed golden set of 15 research questions. Every DOI in every reply must appear in a tool result from that same turn. This is a hard gate, not a metric.
  • ≥90% id-resolution accuracy — the paper the agent talks about is the paper the gateway resolved.
  • 100% retraction flagging on a seeded test set containing known retracted papers.
  • 0 self-contradictions (the “no results… here are results” failure seen in the First Table build).

Quality metrics

  • Seed-set overlap: ≥70% of the agent's top-10 appears in the top-20 a human gets doing the same search manually in the app.
  • Time to first useful shortlist: <2 minutes from a cold, vague question.
  • Hand-off rate: % of conversations where the user opens the session deep link. This is the north-star metric — it measures whether the copilot is feeding the app rather than replacing it.
  • Median tool calls per conversation (cost proxy) and p95 turn latency.
Keep evals/golden-questions.json in the repo and re-run it after every prompt change. The First Table prompt reached 7.3 KB by accumulating fixes; without a regression set, each fix silently breaks something else.

20. Open decisions — we need your call

#DecisionOur recommendation
1Audience: personal/lab tool, or something you intend to share publicly? Build single-tenant first. It changes the auth model completely and it's cheap to widen later.
2Backend: RR private API, OpenAlex, or both? Both, behind one interface. OpenAlex default, RR when authenticated. Non-negotiable if #1 is “public”.

4Writes enabled? (create collections, save articles into the real library) Off for v1. Read-only discovery has all the value and none of the “the bot messed up my library” risk.
5Which app first? MCP server → chatbot → brief generator → digest, per §12.
6Reuse the existing Flowise instance or create a second one? (Stage 3 only) A second agentflow on the same Flowise service costs $0 extra and shares the disk. Only split if you want independent uptime for First Table.
7Do we run Stage 3 at all? Only if the audience includes people who will never install an MCP client. After Stage 2 you already have the research assistant for $14/mo; Stage 3 adds $25/mo plus tokens purely for the packaged chat UI (§13).

That is precisely steps §14.1–§14.5 of Stage 1, so it costs nothing extra: it is the opening of the plan, not a detour.
